## Project identity

Package name is `tokn-on-sol` (legacy). The product is branded **Passly** throughout the UI. Use "Passly" for all user-facing copy, component names, and docs. Don't rename the package.

## Verification workflow

Don't run the dev server or build. Verify changes with:

```bash
npx tsc --noEmit   # type-check
npm run lint       # ESLint (Next.js recommended + TypeScript strict)
npm test           # Vitest; payout fee/hold/idempotency unit tests
```

The user pushes to git and checks Vercel deploys manually.

```bash
npm run create-tree  # Deploy a Merkle tree to whichever network NEXT_PUBLIC_HELIUS_RPC_URL points at
```

## Architecture

Passly is a Next.js 16 App Router application for minting Solana compressed NFT (cNFT) tickets. Buyers pay via Stripe (EUR); a Stripe webhook mints the ticket on-chain. Doormen scan QR codes to verify and redeem tickets.

### Key flows

1. **Purchase** – `/shop/[id]` → `/api/checkout/create` (reserves capacity atomically via `reserve_tickets` SQL function, then creates a 30-min Stripe session; Stripe's minimum lifetime. The buyer-facing hold is **5 minutes** (`HOLD_MINUTES`): enforced on demand; when a reserve attempt hits exhausted capacity, `expireStaleReservations` expires this event's sessions older than the hold via the Stripe API and releases their seats (a session that already completed payment throws on expire and is left alone), then retries once. The shop resume-banner counts down these 5 minutes.) → Stripe webhook `/api/webhooks/stripe` converts the reservation to a sale (`finalize_ticket_sale`), enqueues a `mint_jobs` row and returns immediately. Minting runs async: `after()` in the webhook invocation processes the job (`src/lib/mintJobs.ts`). Because the cron fallback is only **daily** on the Hobby plan (sub-daily crons are not allowed), three buyer-facing surfaces additionally kick the worker whenever they see unfinished work, so a crashed `after()` heals within seconds instead of by 03:30: `/api/checkout/confirm` (polled by the success page), `/api/my-tickets` (any `mint_jobs` row of that buyer still `queued`/`processing`) and `/order/[token]` (guest orders, whose jobs are queued against the **operator** wallet and are therefore invisible to the buyer-wallet check). All three are safe to call on every request — `claim_mint_jobs` is `FOR UPDATE SKIP LOCKED` and skips jobs touched in the last 10 minutes, so polling cannot stampede. The daily cron `/api/cron/mint` remains the final safety net. Max 5 attempts with 2-min backoff, then status `failed` → auto-refund of the unminted share (`autoRefundFailedJob`; skipped when the payout was already transferred or is disputed) + admin alert email with the refund outcome. `checkout.session.expired` releases the reservation; `release_expired_reservations()` in the payout cron is the safety net for missed expiry webhooks.
1b. **Guest checkout** (since 2026-07-29) – **pay first, create the account afterwards**. The default path for signed-out visitors on `/shop/[id]`: `/api/checkout/create` accepts `guest: true` instead of `buyerWallet`, the cNFT is minted to the **operator wallet** (escrow), and the buyer gets a `/order/<token>` link by mail. `guest_orders` (token, stripe_session_id, event_id, email, lang, claimed_at, claimer_wallet) is written by the completed-webhook *before* the mint job; a failure there aborts like the payout row so Stripe redelivers.
   - **`/order/[token]` shows no scannable code.** Signing in is what unlocks the ticket: `POST /api/guest-order/claim` (needs the token **and** a Privy session owning the target wallet) transfers every ticket of the order out of escrow, then the normal rotating QR on `/tickets/[assetId]` takes over. An earlier version rendered a static operator-signed QR on that page so no account was ever needed; it was dropped on 2026-07-29 because a static code is copyable and the link carrying it travels by e-mail. Don't reintroduce it — the login is the point, and every ticket stays on the rotating-QR model.
   - **The claim mints a fresh ticket; it does not transfer the escrowed one.** Bubblegum's `transfer` clears the operator delegation, and that delegation is what lets Passly move a ticket without the owner signing — so a transferred ticket could never afterwards be shared by link or re-issued by support. Measured on live assets: freshly minted tickets have the operator as delegate, transferred ones have none. The escrowed cNFT is left behind in the operator wallet, inert (a guest never held a code for it). The claim route repoints the existing `purchases` row to the new `asset_id`, so the order keeps exactly one row per ticket.
   - The claim route is partial-safe: each ticket is its own mint, tickets that were handed over stay handed over, and `claimed_at` is only set once nothing is left, so a retry finishes the rest. **`claimer_wallet` doubles as the mutex**: it is claimed by a compare-and-swap *before* the first transfer, because reading `claimed_at` alone let two concurrent claims from two different signed-in wallets both enter the transfer loop. The guard re-admits the wallet already mid-claim (so a retry completes the remainder) but locks out a second one; a permanently failed claim therefore keeps the order bound to that wallet, which is deliberate — tickets may already have moved there — and an admin clears `claimer_wallet` to release it.
   - `events.guest_checkout_enabled` (default true) lets an organizer require the account up front instead. Backup-ticket PDFs are unavailable *before* claiming by construction (they need the buyer's own wallet); the shop, success page and confirmation mail all say the account is needed to unlock the ticket, so nobody turns up at the door with just the mail.
1c. **Box office** (since 2026-07-29) – selling at the door for cash, from the **doorman page** (`BoxOffice.tsx`, shown when online and a snapshot is loaded), not the dashboard: that is where a box office physically is, and door-link staff can work it without the organizer's login (`requestMayWorkTheDoor` gates `POST /api/organizer/box-office`). Capacity runs through the unchanged `reserve_tickets` → `finalize_ticket_sale` pair with a synthetic `box_<uuid>` session id, so there is exactly one overselling gate in the system. **No money moves through Passly**: no Stripe session and no `payouts` row — the cash stays with the organizer, and `purchases.source = 'box_office'` keeps these sales separable from card revenue (the Pro analytics compute revenue purely from `payouts` and would otherwise be skewed). `mint_jobs.source` / `mint_jobs.admit_immediately` carry the flags into the purchase rows; `admit_immediately` sets `redeemed_at` at mint time, because the walk-up guest is standing at the door and scanning a code you just handed them is theatre. With an e-mail, the buyer also gets a `guest_orders` link and can move the ticket into an account later. The door snapshot now carries `tiers` so the panel can sell straight from cached data.
   - **Price parity with online is deliberate** (since 2026-08-15): the door collects face price **plus whatever share of the service fee an online buyer pays for this event** (`splitServiceFee` against `events.fee_payer`, which travels through the door snapshot; shown as its own line in `BoxOffice.tsx`). Passly's take does not move with the mode, so the `platform_fees_due` row is the **full** fee in all three cases — only the guest's cash total changes. A cheaper door trains guests to skip the online sale. Since the organizer pockets the whole cash amount, the fee share is booked as a `platform_fees_due` row and **subtracted from their next online payout transfer** (`src/lib/platformFees.ts`, applied in `/api/cron/payouts`) — otherwise the incentive just moves from the guest to the organizer. Don't reintroduce a face-value-only door price.
     - Dues are settled **whole rows only** and never shrink a transfer below `MIN_TRANSFER_CENTS` (€1; Stripe rejects a €0 transfer); leftovers roll to the next payout. Claimed before the transfer, released again (`releaseOffset`) when it fails, and `claimOffsetForPayout` re-collects dues already stamped with this payout id so a retry computes the **same** amount — the Stripe idempotency key is derived from the payout id, and a differing amount under the same key errors.
     - An organizer with no online sales accumulates dues that never settle; that's the known v1 gap. Visible to them as the „Servicegebühr Abendkasse" KPI on `/dashboard/payouts` (`summary.outstandingFees`), so the deduction is never a surprise.
1d. **Season pass** (since 2026-07-29) – one ticket, many dates. `season_passes` is the sellable product, `season_pass_events` its dates, and `pass_redemptions (purchase_id, event_id)` the admission log; `purchases.season_pass_id` marks the ticket while `purchases.event_id` stays NULL (that column is nullable now, guarded by the check constraint `event_id is not null or season_pass_id is not null`). Details in `src/lib/seasonPass.ts`.
   - **`purchases.redeemed_at` is not used for passes.** It is single-use and could only ever admit to one date. The verify route falls through to the pass branch when the atomic `redeemed_at` update matches nothing, then checks `season_pass_events` for the scanned event and inserts into `pass_redemptions`; the unique index on `(purchase_id, event_id)` is the once-per-date gate, exactly as `redeemed_at IS NULL` is for a normal ticket. A pass for a different series reads as `Ticket not found`, so the door learns nothing about tickets it may not scan.
   - **Capacity v1 is the pass's own pot** (`season_passes.capacity`); a pass claims NO seats in its events. Hard room limits would need a block reservation per date — deliberately postponed. Counters move only via `reserve_pass` / `unreserve_pass` / `finalize_pass_sale` / `release_sold_passes`; `release_reservation`, `refund_ticket_sale` and `release_expired_reservations` were **extended** rather than duplicated (they read the reservation row, so every existing caller — expiry webhook, refund path, payout cron — handles passes with no change).
   - **Checkout is its own route** (`POST /api/checkout/pass`), not a branch of `/api/checkout/create`: the ticket route weaves together tiers, discount codes, the waiting room and guest escrow, and a pass shares none of it. v1 has no guest checkout (a pass must live in the buyer's own account to survive the series), no discount codes, no queue, and **no return** (`checkOfferEligibility` rejects passes: a pass spans many dates and has no single seat to give back). Session metadata carries `purpose: 'season_pass'`; the webhook branches on it before the primary ticket path (like subscriptions do) into `handlePassCompleted`. Session **expiry** deliberately falls through to the generic `release_reservation`.
   - **Payout hold is anchored on the purchase date**, not an event date (`computeAvailableAt("", pass.payout_hold_days)`): a pass spans many dates, and holding the money until the last one would turn a season sale into a season-long loan. `payouts.season_pass_id` names the row where `event_id` is NULL. Like box-office sales, pass revenue is invisible to the Pro analytics, which query `payouts`/`purchases` by `event_id` — same known gap, to be closed with the C2 accounting export.
   - **Doorman**: the snapshot folds pass tickets into its normal `tickets` list with `p: 1` and `r` resolved *for this date*, so `offline.ts` needs no pass logic at all; `/api/tickets/redeem-offline` writes `pass_redemptions` for them on sync. Backup-ticket PDFs work for passes (the token verifies through the same pass branch) and print the series instead of a single date.
   - UI: organizer CRUD at `/dashboard/passes` (+ `GET/POST/PUT/DELETE /api/organizer/passes`, free for every approved organizer) reached from a card on `/dashboard` — the topbar link alone scrolls out of view on narrow screens. Buyers reach a pass from **three** places, because a pass is bought on its own page and is otherwise invisible: a section on `/events`, one on the organizer's `/@handle` profile, and a teaser above the buy box on every member event's `/shop/[id]`. Public sale page `/pass/[id]` (+ `/success`), own section on `/my-tickets`, per-date list with admission state on `/tickets/[assetId]`.
2. **QR verification** – `src/app/tickets/[assetId]/TicketClient.tsx` generates a QR code by signing a challenge with the buyer's embedded Solana wallet (Ed25519). Doorman page (`/doorman/[eventId]`) scans it with jsQR and calls `/api/tickets/verify`.
   - Token format: compact JSON `{ a: assetId, t: minuteTimestamp, w: walletAddress, s: base58Signature }`
   - Challenge signed by the wallet: `` `passly:verify:${assetId}:${t}` `` where `t = Math.floor(Date.now() / 60000)`
   - The doorman POSTs `{ token, eventId }` with its organizer Privy Bearer token **or** a door-access-link token (`x-door-token` header). `/api/tickets/verify` is **door-gated**: it loads the event and requires `requestMayWorkTheDoor` (`src/lib/doorAccess.ts`; organizer `requestOwnsWallet` OR a valid `door_access_links` row for exactly this event) before doing anything (a valid QR alone must not let a stranger burn a ticket). Keep this gate. Door tokens unlock ONLY the door surface (verify, snapshot, redeem-offline); never other organizer routes.
   - Verify route steps: (0) organizer auth for `eventId`, (1) replay protection; accept current or previous minute, (2) reconstruct challenge, (3) verify Ed25519 signature via `crypto.subtle`, (4) on-chain ownership check via Helius DAS, (5) atomic redemption; sets `redeemed_at` only if currently NULL, scoped to `event_id = eventId`.
   - **Re-entry** (since 2026-08-04, opt-in per event): festivals, clubs with a yard, anything where guests step outside. `events.reentry_enabled` turns admission from a boolean into a direction: the same QR scanned again checks the guest **out**, the next scan checks them back **in**. While the toggle is off the verify route runs exactly the code it always ran — a second scan stays a rejected duplicate. Details in `src/lib/reentry.ts`.
     - The log is `ticket_scans` (append-only, one row per scan). `purchases.redeemed_at` / `pass_redemptions` keep their old meaning — "was admitted at least once", written by the first `in` — so badges, the snapshot, the dashboard counters and the analytics are untouched by the toggle. **Don't clear `redeemed_at` on an exit**; nothing downstream expects it to go back.
     - `events.reentry_cooldown_seconds` (0–3600, default 120) is the anti-abuse part: a ticket cannot flip state again until it passes, so one QR can't be waved past the scanner to walk a queue of people in. Enforced inside `record_ticket_scan`, which locks the purchase row before deciding — two doormen scanning the same ticket at once can never both write an `in`.
     - Tickets admitted **before** re-entry was switched on have no scan rows; their redemption state stands in for "inside", so their next scan is an exit. Same fallback in the SQL function and in the door snapshot.
     - Offline: the snapshot carries `reentry` plus each ticket's side of the door (`d`) and last scan (`ls`); the device toggles locally and enforces the cooldown against snapshot + its own queue. Queue entries gained an `id` (a re-entry event queues several scans per ticket, so the asset ID stopped identifying an entry) and a `direction`, which the sync replays as-is — re-checking the cooldown server-side against a later `now` would silently drop legitimate scans.
     - The buyer's ticket page says so (`ticket.reentryHint`): a guest who walks out **without** scanning gets checked out on the way back in. The door staff can't fix that inside the cooldown, so telling the guest is part of the feature, not decoration.
   - **Backup tickets** (offline fallback for venues without connectivity): static token `{ a, w, s, b: 1, p: { f, l, d } }`; no time window by design; once-only redemption + personalization (name/birth date, ID check at the door) carry the security. The identity `p` (firstName/lastName/birthDate) is **bound into the signed challenge** so it can't be edited on the shared QR or the printed PDF: challenge = `backupChallenge(assetId, person)` in `src/lib/backupChallenge.ts` (client-safe; the single source of truth used by the modal, the issue route, the verify route and the offline verifier). New tokens sign `` `passly:backup:${assetId}:${firstName}|${lastName}|${birthDate}` ``; legacy tokens (no `p`) still sign the bare `` `passly:backup:${assetId}` `` and keep verifying (no downgrade: stripping `p` breaks the person-bound signature). Issued via `POST /api/tickets/backup` (auth = the signatures themselves; personalization is embedded in the QR + printed/mailed, never stored in our DB) → PDF (`src/lib/backupTicket.ts`, pdf-lib) as download + mail attachment. UI: `BackupTicketModal` on the checkout success page. Verify route and doorman offline verifier both accept `b: 1` and return the `person`; on a valid backup scan the **doorman pauses on the result**, displays name + birth date from the (signed) QR and does not resume scanning until the doorman taps "Ausweis passt, Einlass" (`awaitConfirm`/`confirmAndResume` in `/doorman/[eventId]`). Non-backup scans keep the 3 s auto-advance.
   - `NEXTAUTH_SECRET` is present in env but **not used** for QR verification (legacy name, do not remove; may be referenced elsewhere).
3. **Organizer gate** – New organizers apply at `/become-organizer`. The POST handler at `/api/organizers/apply` verifies the Privy auth token server-side (`@privy-io/server-auth`), checks that the user has a verified email address on their Privy account, then inserts into the `organizers` table at `status: 'pending'` (+ admin alert e-mail). **Approval is manual** (fraud gate; since 2026-07-14): the admin reviews at `/admin/organizers` (`ADMIN_SECRET`-gated, API `/api/admin/organizers`), approve/reject sends the applicant a decision e-mail (`sendOrganizerApplicationDecision`). `/become-organizer` renders pending/rejected states; `/dashboard` and all organizer APIs require `status: 'approved'`.
4. **Organizer dashboard** – `/dashboard` lets approved organizers create events (saved to Supabase) and view sales. `/api/events/create` requires a Privy Bearer token proving ownership of `organizer_wallet` (`requestOwnsWallet` in `src/lib/privyServer.ts`; use this helper for any new writing organizer route). Events can be marked **private** at creation; private events are excluded from the public listing but remain purchasable via direct link.
5. **Organizer public profiles & verification** (since 2026-07-24) – Approved organizers get a YouTube-channel-style public page at `getpassly.de/@<handle>` (`src/app/[handle]/page.tsx`, a root dynamic segment; real routes win routing priority, and it `notFound()`s anything not a valid `@handle`; `+ opengraph-image.tsx`). They edit it at `/dashboard/profile` (banner, avatar, `public_name`, `@handle`, `bio`, links = **free**; accent colour + featured event = **Pro**) via `GET/PUT /api/organizer/profile` (`requestOwnsWallet` + approved; Pro fields stripped server-side when `plan !== 'pro'`; `featured_event_id` ownership-checked). Handle rules live in `src/lib/organizerHandle.ts` (client-safe: `HANDLE_RE`, `RESERVED_HANDLES`, `validateHandle`); uniqueness is a case-insensitive DB index (`23505` → 409 `handle_taken`). Images upload via `POST /api/organizer/profile/upload-image` (`kind=avatar|banner`) reusing `uploadProfileImage` in `src/lib/eventMetadata.ts` (same `event-assets` bucket, `avatars/`|`banners/` prefixes). **Two-tier trust badges:** every approved organizer keeps the "Geprüft" chip; admin-verified brands additionally get a **purple check** (`VerifiedCheck` in `passlyUi.tsx`) + the admin-written `verified_label`, shown on the profile, the shop page and the dashboard header. Verification is admin-only: `POST /api/admin/organizers` action `verify` (requires `verifiedLabel`) / `unverify` (`x-admin-secret`; independent of the pending/approved lifecycle). Admin lookup of any organizer's events: `GET /api/admin/organizers/events?wallet=`, surfaced as an expandable row + search box in `OrganizersTab.tsx`. `/api/organizers/status` also returns `handle/public_name/is_verified/verified_label` for the dashboard header. Public pages read via `supabaseAdmin` with explicit public-only column selects (never `stripe_*`/`email`).

### Authentication & wallets (Privy)

The root layout is a **server component** (global `metadata`/OG tags); `PrivyProvider` + consent banner live in the client component `src/app/components/Providers.tsx`, which wraps everything. Login method is **email only** (`loginMethods: ['email']`). Email login auto-creates a Solana embedded wallet per user. All auth-gated pages check `usePrivy().authenticated` client-side. Server-side token verification uses `PrivyClient` from `@privy-io/server-auth` (requires `PRIVY_APP_SECRET`).

### Blockchain

- **Network**: decided solely by `NEXT_PUBLIC_HELIUS_RPC_URL` via `heliusRpcUrl()` in `src/lib/solana.ts`; never hardcode an RPC host. Local `.env.local` points at **Mainnet** (verified 2026-07-30: the configured tree exists on mainnet holding real rent and does not exist on devnet). The stale `.env` still says devnet with the old single tree `FcXGj…` — `.env.local` wins locally; don't "fix" one from the other. Trees and the operator key are per-network: a network switch needs new trees and a funded operator wallet on that network.
- **Minting**: `src/lib/mint.ts`; Metaplex Bubblegum cNFTs. The operator keypair (`OPERATOR_PRIVATE_KEY`) signs every mint; the buyer's embedded wallet receives the cNFT as `leafOwner`. The buyer never signs; don't change this to client-side signing.
  - Every mint carries a **priority fee** (`withPriorityFee` in `mint.ts`, applied to tickets *and* badges). Without it a transaction has only the 5000-lamport base fee and can fail to land for minutes during mainnet congestion, which the worker's retries hide slowly before auto-refunding a buyer whose ticket was fine. `PRIORITY_CU_LIMIT` (250 000) and `priorityFeeMicroLamports()` (default 50 000, override via `SOLANA_PRIORITY_FEE_MICROLAMPORTS`) live in `src/lib/operatorBalance.ts` — the same module the admin balance route and the payout cron read, so the per-mint cost estimate can never drift from what a mint actually costs. **The CU limit is a cost multiplier**: the fee is charged on the *requested* limit, not the units consumed, so raising it "to be safe" raises the price of every mint.
- **Merkle trees**: `MERKLE_TREE_ADDRESSES` (comma-separated; each mint picks one at random via `pickMerkleTree()`; spreads concurrent mints so tree transactions don't conflict). Legacy fallback: `MERKLE_TREE_ADDRESS`. `npm run create-tree` creates one tree on the network `NEXT_PUBLIC_HELIUS_RPC_URL` points at (depth 14 = 16,384 tickets; **~0.222 SOL rent on mainnet**, measured on the live account — the "~0.1 SOL" in the script's own comment is wrong. `maxBufferSize: 32` instead of 64 would roughly halve it and is still ample for this volume). Adding a tree is purely additive: append the address to the env var, `pickMerkleTree()` uses it immediately, existing assets are untouched. Trees serialise per slot under Solana's write lock, so more trees = more concurrent mint throughput.
- **Asset queries**: Helius DAS API (`HELIUS_API_KEY`) for ownership and metadata lookups; always fetched with `cache: 'no-store'`.
- **cNFT metadata**: static per-event JSON in the public Supabase Storage bucket `event-assets` (`metadata/<eventId>.json`, written by `uploadEventMetadata` in `src/lib/eventMetadata.ts` during `/api/events/create`; `events.metadata_uri` stores the URL, `events.image_url` the optional event image uploaded via `/api/events/upload-image`). The mint uses `metadata_uri`; the legacy dynamic route `/api/tickets/metadata?name=&date=` remains as fallback for events created before it existed (their minted assets point at it on-chain; don't remove).
- **cNFT metadata attributes**: use `trait_type: "Event Name"` and `trait_type: "Event Date"` (two words, title-case). All writers (`uploadEventMetadata`, `/api/tickets/metadata`) and the reader `/tickets/[assetId]/page.tsx` must match these exact strings.

### Database (Supabase)

Tables:
- `events`: `id, organizer_wallet, name, date, start_time, price_eur, capacity, tickets_sold, tickets_reserved, is_private, payout_hold_days, image_url, metadata_uri, venue, description, accent_hue, border_style, cancelled_at, reminder_sent_at, created_at`
  - `accent_hue` (smallint 0–360, nullable) / `border_style` (text, nullable, one of `BORDER_STYLES`): per-event card styling, validated in `/api/events/create` + `/api/events/update`. `border_style` is Pro-only (stripped server-side on the free plan), `accent_hue` is free.
  - `start_time text` (nullable, `HH:MM`, Europe/Berlin); optional event start; shown on shop/ticket/listing pages, in the reminder mail and in the calendar export `GET /api/events/[eventId]/ics` (public .ics download, linked from ticket + checkout-success pages; all-day entry when NULL).
  - `reminder_sent_at`; once-only claim for the day-before reminder e-mail batch (`sendDueEventReminders` in `src/lib/reminders.ts`, runs inside the payout cron because both Hobby cron slots are taken; recipients via purchases→mint_jobs like the organizer messaging).
  - `is_private boolean default false`; private events are excluded from the public listing (`/events`, `sitemap.ts`, the anon RLS policy) but still purchasable via direct link.
  - `image_url` / `metadata_uri`; public Supabase Storage URLs (bucket `event-assets`); `metadata_uri` is stamped on-chain at mint, NULL for pre-existing events (mint falls back to the legacy dynamic metadata route).
  - `payout_hold_days int default 0 (0–90)`; days after the event date before ticket revenue is transferred to the organizer (chargeback protection). 0 = transferred by the next daily payout cron.
  - `reentry_enabled boolean default false` / `reentry_cooldown_seconds int default 120 (0–3600)`; guests may leave and come back, see **Re-entry** above. Set in `/api/events/create` + `/api/events/update`, edited in `EventEditor` ("Wiedereinlass (Re-Entry)", cooldown entered in minutes). Free for every organizer.
  - `fee_payer text default 'buyer'` (`buyer` | `split` | `organizer`): who carries the service fee, see **Fees** above. Validated in `/api/events/create` + `/api/events/update`; the update route checks the **effective** state (payload merged with what's in the DB), because `fee_payer` and the tiers arrive in independent requests. Free for every organizer. A paid tier must cost at least `minUnitPriceCentsFor(payer)` (52 cents for `split`, 105 for `organizer`) or the organizer would keep nothing.
  - `resale_enabled boolean default false`: lets guests give a ticket back so the seat can be sold again (see **Ticket return & resale** below). The legacy `resale_max_markup_pct` column still exists but is **unused** — the return model has no markup.
  - `tickets_reserved int default 0`; capacity claimed by open checkout sessions. Available = `capacity - tickets_sold - tickets_reserved`. Never update `tickets_sold`/`tickets_reserved` directly from code; always go through the SQL functions `reserve_tickets`, `unreserve_tickets`, `finalize_ticket_sale`, `release_reservation`, `release_expired_reservations` (atomic, race-free).
  - `capacity` / `price_eur` are the **aggregate** over the event's tiers since 2026-07-07: capacity = sum of tier capacities, price_eur = min tier price ("ab"-price for listings). The tier is the price authority at checkout.
  - `cancelled_at`; set once via `/api/events/update` (action `cancel`): sales stop (checkout 410), event leaves the public listing, every not-yet-transferred charge is refunded in full (the `charge.refunded` webhook does revoke + seats), free-ticket purchases revoked directly, open sessions expired. Payouts in `paid`/`disputed` are reported for manual handling, not auto-refunded.
- `ticket_scans`: the re-entry in/out log; `id, purchase_id, event_id, direction ('in'|'out'), scanned_at, created_at`. Written only by the SQL function `record_ticket_scan` (service-role only, locks the purchase row, enforces the cooldown, writes `redeemed_at`/`pass_redemptions` on the first `in`). Empty for events without `reentry_enabled`. See **Re-entry** above.
- `ticket_tiers`: price categories per event; `id, event_id, name, price_eur, capacity, tickets_sold, tickets_reserved, sort`. Every event has ≥1 tier (legacy events got a backfilled 'Standard' tier); max 5, names unique per event. Tier counters follow the same rule as event counters: only via the SQL functions (all take an optional `p_tier_id` and keep tier + event aggregate in sync; the event-level total remains the hard overselling gate). Editing: capacity can't drop below sold+reserved, tiers with sales can't be deleted.
- `ticket_reservations`: one row per checkout session; `stripe_session_id (PK), event_id, tier_id, quantity, status (reserved|finalized|released|refunded), expires_at`. State transitions happen only inside the SQL functions above.
- `mint_jobs`: async mint queue; `stripe_session_id (unique), event_id, tier_id, buyer_wallet, buyer_email, quantity, status (queued|processing|done|failed), attempts, last_error, refund_id`. Claimed via `claim_mint_jobs(limit, max_attempts)` (FOR UPDATE SKIP LOCKED). `refund_id` is the once-only gate for the auto-refund on permanent failure. Worker: `src/lib/mintJobs.ts`.
- `purchases`: `event_id, tier_id, buyer_wallet, asset_id, stripe_session_id, source, redeemed_at, revoked_at`; `revoked_at` is set when the charge is fully refunded; the doorman verify route rejects revoked tickets. `stripe_session_id` is **nullable** since 2026-07-29 (box-office sales have no Stripe session); `source` is `online` | `box_office` — where the sale happened. `event_id` is nullable too: a season-pass ticket sets `season_pass_id` instead, and `redeemed_at` stays NULL for it (admission lives in `pass_redemptions`). Guest-vs-account is a *different* axis and is derived from `guest_orders`, not from `source`.
- `queue_tokens`: virtual waiting room for on-sales; `id, event_id, token (unique bearer), seq (bigserial, the ordering), admitted_at, expires_at, created_at`, plus `events.queue_enabled` / `events.queue_slots` (default 50). SQL function `admit_from_queue(event_id, hold_minutes)` promotes waiting tokens in `seq` order until `queue_slots` buyers hold a live slot (`FOR UPDATE SKIP LOCKED`, so concurrent callers never double-admit); `purge_stale_queue_tokens()` is housekeeping in the payout cron. **Every status poll drives the promotion**, so the line advances whenever anyone is watching and no cron is needed for the normal case. `/api/queue` is both halves (POST join, GET status) and is unauthenticated on purpose — a buyer joins before deciding anything, and holding a token grants nothing except the right to reach `/api/checkout/create`, which does all the real checks. That route rejects a checkout with `queue_required` (409) when `queue_enabled` and the token isn't currently admitted, checked *before* the reservation so a queue-jumper can't take capacity. Built on Postgres rather than Redis to stay inside the Hobby plan.
- `season_passes` / `season_pass_events` / `pass_redemptions`: the season pass; `season_passes(id, organizer_wallet, name, description, price_eur, capacity, tickets_sold, tickets_reserved, active, image_url, metadata_uri, payout_hold_days, created_at)`, `season_pass_events(pass_id, event_id)` (PK on both, cascade), `pass_redemptions(id, purchase_id, event_id, redeemed_at, unique(purchase_id, event_id))`. See **Season pass** above. `purchases`, `mint_jobs`, `ticket_reservations` and `payouts` each carry a nullable `season_pass_id`; on all four `event_id` is nullable.
- `guest_orders`: one row per guest checkout; `id, token (unique bearer), stripe_session_id (unique), event_id, email, lang, created_at, claimed_at, claimer_wallet`. See **Guest checkout** above.
- `claims`: one-time transfer links (ticket sharing, support re-issue); `asset_id, token (unique bearer), seller_wallet, claimed_at, claimer_wallet`. Created by `/api/claims/create` (Privy-auth, on-chain ownership checked) and `/api/admin/reissue`; redeemed via `POST /api/claims/[token]` (atomic `claimed_at IS NULL` update, then operator escrow → claimer, then `purchases.buyer_wallet` repointed). The token IS the credential; anyone holding the link can claim, by design.
- `organizers`: `id, wallet_address, email, name, type (private|business), business_name, status (pending|approved|rejected), stripe_account_id, stripe_charges_enabled, stripe_payouts_enabled, plan (free|pro), stripe_customer_id, stripe_subscription_id, plan_period_end, plan_cancel_at_period_end, created_at` + **public-profile columns** (since 2026-07-24): `handle` (unique lowercase, `^[a-z][a-z0-9_]{2,29}$`, case-insensitive unique index; public URL `getpassly.de/@<handle>`), `public_name`, `bio`, `avatar_url`, `banner_url`, `links` (jsonb `[{label,url}]`, max 5; free), `accent_hue` (smallint 0–360, Pro), `featured_event_id` (uuid FK→events, Pro), `is_verified` (bool, admin-set brand check), `verified_label` (admin-written text next to the purple check). See **Organizer public profiles & verification** below.
- `badges`: buyer achievements; `id, wallet_address, badge_type, asset_id, earned_at, event_id, organizer_wallet` (partial unique indexes dedupe awards; see Badges section)
- `organizer_messages` / `organizer_campaigns` / `loyalty_programs` / `loyalty_claims` / `analytics_events`: see Dashboard Pro & analytics sections
- `profiles`: buyer/organizer account profile; `wallet_address (PK), display_name, bio, is_private`. Edited on `/account` (GET/PUT `/api/profile`, auth `requestOwnsWallet`); read server-side by the public profile `/collection/[walletAddress]` (`is_private` hides the page, `display_name` replaces the wallet ID). `ProfileNudge` (mounted on `/my-tickets` + `/dashboard`) prompts accounts without a display name once per device; `AccountMenu` is the avatar dropdown in all signed-in topbars.
- `payouts`: one row per paid checkout session; `stripe_session_id (unique), payment_intent_id, charge_id, event_id, organizer_wallet, stripe_account_id, gross_cents, fee_cents, buyer_fee_cents, net_cents, currency, available_at, status (pending|paid|held|disputed|failed|refunded), transfer_id, dispute_id, failure_reason, payment_method`
  - `buyer_fee_cents`: the buyer's share of `fee_cents`; NULL on rows written before `events.fee_payer` existed, which means the buyer paid all of it. The receipt derives the ticket price as `gross_cents − coalesce(buyer_fee_cents, fee_cents)` — never from `net_cents`, which is the organizer's yield and differs from the price whenever they carry part of the fee. Partial refunds rescale it by the same ratio as `fee_cents`.
  - `payment_method`: Stripe `payment_method_details.type` of the funding charge (`card`, `paypal`, `klarna`, …), resolved by the webhook via `expand: ['latest_charge']`. NULL on rows written before the column existed. Non-card methods settle on their own schedule, so a `source_transaction` transfer can fail purely because the funds aren't available yet; the payout cron puts the method into the held-payout alert so that case is recognisable.
- `discount_codes`: Pro feature; `id, event_id, code (unique per event, case-insensitive), percent_off (1–100; 100 = guest list), max_uses (soft cap), uses, active`. Validation authority: `findValidDiscount`/`discountedUnitPrice` in `src/lib/discounts.ts`, used by BOTH `/api/checkout/validate-code` (public preview, rate-limited) and `/api/checkout/create` (`discountCode` in body scales the tier price + recomputes the service fee; metadata `discountCodeId`/`discountPercent`). Uses are incremented by the completed webhook via SQL function `increment_discount_uses` (webhook idempotency claim = dedupe). CRUD: `/api/organizer/discount-codes` (Pro-gated); DELETE deactivates.

Signup: `POST /api/waitlist/join` (public, rate-limited, only when sold out AND organizer plan = pro; shop page shows the form via server-side plan check). Notification (`src/lib/waitlist.ts`): `notifyWaitlistIfSeats` claims entries atomically (notified_at while NULL) and mails "wieder verfügbar"; hooked into `charge.refunded` (full refund), `checkout.session.expired`, and the daily `sweepWaitlists` in the payout cron. One mail per entry, ever; the mail reserves nothing.
- `door_access_links`: time-limited doorman access; `id, event_id, token (unique plaintext bearer), label, expires_at (event date + 2 days), revoked_at`. Managed via `/api/organizer/door-links` (GET/POST/DELETE, organizer-gated, max 10 active/event; DELETE revokes instead of deleting). Doorman opens `/doorman/[eventId]?key=<token>` without Privy login; the key is validated via the snapshot route.
- `platform_fees_due`: service fees the organizer collected in cash and owes Passly; `id, organizer_wallet, event_id, season_pass_id, session_id (unique), source, quantity, fee_cents, currency, status (pending|settled|waived), settled_payout_id, settled_at, created_at`. Written by the box-office route, consumed by the payout cron. See **Box office** above.
- `stripe_webhook_events`: processed Stripe event IDs (`id` = evt_… primary key); the webhook idempotency gate.
- `resale_offers`: Rückgabe-Angebote ("Rückgabe & Neuverkauf"); `id, purchase_id, asset_id, event_id, tier_id, seller_wallet, origin_session_id, origin_charge_id, origin_payment_intent_id, paid_cents, return_fee_cents, refund_cents, currency, status (active|sold|withdrawn|expired), refund_id, sold_session_id, sold_at, refunded_at, closed_at`. Partial-unique index on `asset_id WHERE status = 'active'`. Claimed via `claim_resale_offer` (FOR UPDATE SKIP LOCKED); seats move via `release_sold_seats` / `reclaim_sold_seat`. See **Ticket return & resale** below.

### Stripe Connect payouts

- **Model**: Separate Charges & Transfers (NOT destination charges); rationale documented in `src/lib/payouts.ts`. The platform charges the buyer; the webhook writes a `payouts` row; `/api/cron/payouts` (Vercel Cron, daily 03:00 UTC, auth `Bearer CRON_SECRET`) transfers `net_cents` to the organizer's Express account once `available_at` has passed, using `source_transaction` and idempotency key `payout-transfer-<payout id>`. Outstanding `platform_fees_due` (box-office cash) are **subtracted from that amount** before the transfer — see **Box office** above for the claim/release protocol.
  - The run **drains in batches** (100 rows per query, max 10 batches, and it stops after ~240 s of the 300 s `maxDuration` so it can never be killed mid-transfer). There is one payout row per checkout session, so a single sold-out event can produce more due rows than one page holds; capping the run at one page would have left the remainder waiting another 24 h each. Processed rows leave `status = 'pending'`, so re-running the same query returns the next block. The response reports `batches` and `remaining: true` when a budget was hit.
  - The same cron reports **operator-wallet health** (`reportOperatorHealth`): a low SOL balance or nearly-exhausted Merkle trees stop *all* minting system-wide, and the only other signal would be one permanently-failed mint job per order after five attempts each. Thresholds live in `src/lib/operatorBalance.ts`; the check swallows its own errors so an unreachable RPC never turns a successful payout run into a failed cron.
- **Payment methods**: the checkout routes deliberately do **not** set `payment_method_types`. That omission is what activates Stripe's dynamic payment methods, so whatever is enabled in the Stripe Dashboard (card, PayPal, Apple/Google Pay, Klarna) appears in checkout with no code change. Setting `payment_method_types` would silently pin checkout back to cards — don't. The Pro subscription (`mode: 'subscription'`) stays card-only; PayPal can't back it.
- **Fees**: service fee €1.00 + 4% **per ticket** (`src/lib/fees.ts`; client-safe, imported by the shop UI). **Who pays it is a per-event choice** (`events.fee_payer`, since 2026-08-15): `buyer` (default and historical behaviour — added as a second Stripe line item on top of the face price, organizer nets 100%), `split` (half each; the buyer's half floors, the organizer carries the odd cent) or `organizer` (the face price is the final price and the fee comes out of their proceeds). `splitServiceFee(unitPriceCents, payer)` is the authority; only the **buyer's** share becomes a line item. The **full** fee is stored in the session metadata as `serviceFeeCents` and booked as `fee_cents`; `buyerFeeCents` carries the buyer's share into `payouts.buyer_fee_cents`. The invariant that makes every mode work downstream: `gross_cents` = what the buyer paid, `fee_cents` = the full platform take, `net_cents = gross − fee`. `resolveFeeCents` in `src/lib/payouts.ts` is the single decision point (metadata / clamped / legacy) used by all three booking sites — **a fee above the gross is clamped, never reinterpreted as the legacy 3%**, which under an absorbed fee would hand the organizer 97% and make Passly pay its own fee. Sessions without that metadata (pre-fee) fall back to the legacy organizer-side 3% split (`computeFeeSplit`, `PLATFORM_FEE_BPS`; keep for legacy rows). Free tickets carry no fee. Partial refunds rescale fee/net by the payout row's own fee ratio.
- **KYC gate**: organizers can always create events; `/api/checkout/create` returns 503 for paid events until the organizer's Connect account has `charges_enabled`.
- **Failure handling**: failed transfers (restricted account etc.) → status `held`, funds stay on the platform balance. `charge.dispute.created` blocks a pending transfer (`disputed`). Admin resolution UI at `/admin/payouts` (gated by `ADMIN_SECRET`, sent as `x-admin-secret`): retry / release / cancel.
- **Webhook idempotency**: every handled event ID is claimed via PK insert into `stripe_webhook_events` before processing. On payout-row/finalize/enqueue failures the claim is released and a 500 returned so Stripe retries. Mint retries are handled by the `mint_jobs` queue, not by Stripe redelivery.
- **Refunds** (`charge.refunded`): full refund before transfer → payout `refunded` (terminal), tickets revoked (`purchases.revoked_at`), seats freed via `refund_ticket_sale`; partial refund → organizer share recomputed from the remaining amount; refund after transfer → flagged for manual recovery.
- The Stripe webhook endpoint must be subscribed to `checkout.session.completed`, `checkout.session.expired`, `account.updated`, `charge.dispute.created`, `charge.refunded`, `customer.subscription.created/updated/deleted` and (Connect) `payout.paid`, `payout.failed`.

### Ticket return & resale ("Rückgabe & Neuverkauf", since 2026-08-18)

Replaced the C2C secondary market on 2026-08-18. The old design is archived in
`archive/resale-v1/` with its rationale; the tag `resale-v1` marks the last
commit that had it. **Don't reintroduce a C2C market without answering the three
questions that killed it**: merchant-of-record liability on chargebacks, the
ZAG/e-money status of stored value, and the GwG/KYC bar on paying out to a third
party.

The whole model rests on one point: **a refund to the original payment method is
not a payout to a third party**, it is the reversal of a payment the same person
made with an instrument their bank already identified. No KYC, no stored value,
no merchant-of-record role.

- **Flow**: seller offers (`POST /api/resale/offer`) → their purchase is revoked
  and the seat released (`release_sold_seats`) → the next buyer buys through the
  **ordinary** checkout, at the ordinary price → the mint worker claims one open
  offer per delivered ticket (`claim_resale_offer`) → the seller is refunded on
  their original charge. Withdraw via `POST /api/resale/withdraw`; unsold offers
  are handed back by `sweepResaleOffers` in the payout cron on the event day.
- **No markup, by construction.** Stripe never refunds more than the original
  charge, so resale is at the original price only. `events.resale_max_markup_pct`
  is dead; `events.resale_enabled` is the switch. The buyer never sees a
  secondary market — same price, ordinary checkout, so `/shop/[id]` has no
  resale section and there is no resale checkout route.
- **Nothing is transferred on-chain.** The seller's ticket is revoked and the
  buyer gets a **fresh mint**. Two reasons: Bubblegum's `transfer` clears the
  operator delegation (a transferred ticket can never be moved by Passly again —
  see **Guest checkout**), and a revocation invalidates an already-printed
  backup PDF absolutely rather than only via the wallet check. A mint costs
  ~17,500 lamports, far less than the return fee.
- **Return fee**: 10 %, min €1 (`returnBreakdown` in `src/lib/fees.ts`,
  unit-tested, client-safe). Charged against **what the seller actually paid**,
  never the tier's face value — a discounted ticket cannot be refunded at face
  value, and over-refunding is a real loss. Passly's take on a resold seat is
  this fee **plus** the ordinary service fee from the new buyer.
- **The organizer must not be paid twice.** The new buyer's purchase creates an
  ordinary `payouts` row, so `unbookOrganizerShare` reduces the *original*
  payout by that ticket's net share (`gross −= refund`, `net −= net/quantity`,
  `fee = gross − net`, preserving `net = gross − fee`). This is only safe
  because `computeAvailableAt` anchors payouts on the **event date** and returns
  are rejected from the event day onwards — the original payout is therefore
  always still `pending`. If it is somehow `paid`, an admin alert fires instead.
- **The `charge.refunded` webhook must skip these refunds** (checked against
  `resale_offers.origin_charge_id` with a set `refund_id`, not Stripe metadata —
  `charge.refunds` is not reliably expanded on a webhook payload). Its normal
  partial-refund rescaling would take money off an organizer whose seat was
  legitimately resold, and its revocation would hit a row that is already
  revoked by design.
- **Backup tickets**: `purchases.backup_issued_at` (timestamp only, never the
  personalization) is set by `POST /api/tickets/backup` so the return dialog can
  warn precisely those sellers whose printout is about to become worthless.
- **Not supported**: season passes (no single event, no face value), free
  tickets and box-office sales (no `payouts` row means nothing to refund), and
  purchases older than `RETURN_WINDOW_DAYS` (150) because refunds to the
  original card become unreliable after roughly half a year. Box-office sales
  also never *consume* an offer: that cash never passed through Passly, so
  settling one would make Passly refund a seller out of its own pocket.

### Accounting: receipts & export (since 2026-07-29)

Deliberately **no VAT logic**: no rates, no small-business notice, no §14-UStG
mandatory fields. Passly is not the seller of the ticket — the organizer is,
and only they know their own tax situation. Both artefacts say so on their face,
so nobody files them as something they aren't. Don't add tax handling here
without deciding that question first.

- **Receipt PDF** (`src/lib/receipt.ts`, pdf-lib, same visual language as `backupTicket.ts`). `loadReceiptInput(sessionId)` assembles it from the **`payouts` row**, which is the money authority: `gross_cents` is what the buyer owed, `fee_cents` what Passly kept, `net_cents` what the organizer gets, all already adjusted by a partial refund. No payouts row → no receipt, which is correct for free tickets and for box-office cash (that money never passed through Passly; a Passly receipt for it would be a false document). Receipt number is `PSL-<YYYYMMDD>-<last 6 of the session>`.
- **Route** `POST /api/tickets/receipt` takes either `assetId` (gated by `requestOwnsWallet`, since the PDF carries the buyer's e-mail) or `orderToken` (guest orders; the token IS the credential, as on `/order/[token]`). UI: `ReceiptButton` on `/tickets/[assetId]` and `/order/[token]`. The PDF is also attached to the confirmation mail (`sendTicketConfirmation({ receiptPdf })`), built best-effort in `mintJobs` so a broken PDF can never cost the buyer their ticket links.
- **CSV export** `GET /api/organizer/export?walletAddress=&from=&to=` (`requestOwnsWallet`, default range = current calendar year) + the date picker on `/dashboard/payouts`. German Excel format: semicolons, decimal comma, UTF-8 BOM. **Not a DATEV Buchungsstapel** — mappable columns, no accounts and no BU-Schlüssel. Two sources: `payouts` (online tickets + season passes) and `purchases` with `source = 'box_office'` (priced from the tier, `Belegnummer` prefixed `BAR-`; gross = tier price + service fee, because the guest pays the online total in cash, fee = that service fee, payout = the tier price the organizer keeps after the deduction).
- **"davon"-lines in the Pro analytics** (`offBook` in `/api/organizer/analytics`, rendered under the KPI strip): box-office tickets count toward the ticket figures but not the revenue (no `payouts` row), and season passes appear in neither (their payout carries `season_pass_id`, not `event_id`, so every event-scoped query misses them). Both facts are correct and both look like a counting bug without the lines; if a third off-book source ever appears, it belongs in `loadOffBookRevenue` too.

- Types: `first_show/show_5/show_10` (redeemed-ticket milestones), `loyal_organizer` („Stammgast", 3 distinct redeemed events **per organizer**, `badges.organizer_wallet` set), `sold_out_show` (redeemed at a sold-out event); all awarded on redemption (`checkRedemptionBadges`, called from ticket verify AND offline-redeem sync); `first_ticket`/`early_bird` (purchase ≤1h after event creation); awarded at mint time (`checkPurchaseBadges` from `mintJobs`). All calls fire-and-forget.
- Dedupe via partial unique indexes on `badges` (wallet+type global, wallet+type+organizer for Stammgast); inserts tolerate 23505. Badge cNFT minted async (`mintBadge`), images in `public/badges/<type>.png`, metadata route `/api/badges/metadata` (German, immutable-cached).
- `/api/my-tickets` returns a `progress` object (attended count, next milestone, best Stammgast candidate by organizer display name) rendered as progress bars on `/my-tickets`.
- **Nudge-Mail**: `maybeSendBadgeNudge` (in `src/lib/badges.ts`, called at the end of `checkRedemptionBadges`) e-mails the guest after check-in when exactly 1 event remains to the Stammgast badge or the next milestone; only on the wallet's first redeemed ticket at that event (guards against multi-ticket re-sends). Best-effort; never fails the redemption path.
- **Public profile share card**: `/collection/[walletAddress]/opengraph-image.tsx` renders the OG image (name, attended count, badge symbols); private profiles get a generic card. `generateMetadata` on the page supplies title/description; `ShareButton` (client) does navigator.share/clipboard.

### First-party analytics (consent-gated)

- Cookies `passly_consent` (`granted|denied`, 12 months) + `passly_cid` (UUID, only while granted); set client-side by `ConsentBanner` (`src/app/components/ConsentBanner.tsx`, mounted in the root layout with `PageViewTracker`). `track()` in `src/lib/track.ts` is a no-op without consent.
- `POST /api/track` requires both cookies, enforces an event-name allowlist (`page_view`, `ticket_selected`, `checkout_started`, `purchase_completed`, `ticket_viewed`), caps props at 1 KB, always answers 204. Table `analytics_events` (no wallets/e-mails/IPs; `cid` is the only identifier). `referrer` feeds the Pro channel attribution — organizers only ever see aggregates.
- `/datenschutz` Ziffer 10 documents the cookie + withdrawal (`ConsentSettingsButton`); the page and any tracking change MUST ship in the same deploy. Doorman pages are never tracked.
- **Alerting**: operational failures e-mail `ADMIN_ALERT_EMAIL` via `sendAdminAlert` (src/lib/email.ts); held transfers (payout cron), refund-after-transfer, dispute created, refund/payout-row webhook failures, Connect bank-payout failures, unresolved refunds on event cancellation, permanently failed mint jobs. Always fire-and-forget (`void …().catch(…)`), never block the money path on Resend.

### Doorman offline buffer

`/doorman/[eventId]` keeps admitting guests without connectivity: while online it refreshes a ticket snapshot every 60 s (`/api/organizer/event/snapshot`, cached in localStorage). When the live verify call fails (5 s timeout), verification runs locally (`src/app/doorman/[eventId]/offline.ts`): same Ed25519 challenge + minute window as the server, ownership against `purchases.buyer_wallet` (kept current by claims), once-only redemption against snapshot + local queue. Queued offline scans sync via `/api/tickets/redeem-offline` (atomic redeem; conflicts reported when another device was first). Known trade-off: two offline devices can't see each other's scans.

### Support

- `/hilfe`; public FAQ + support address (`NEXT_PUBLIC_SUPPORT_EMAIL`, default support@getpassly.de), linked from all footers.
- **Ticket re-issue** (buyer lost e-mail access): verify identity out-of-band (Stripe receipt), then `POST /api/admin/reissue` (`x-admin-secret`, body `{"assetId"}`) → returns a one-time claim link for the buyer's new account. Uses the existing claims/escrow flow; blocked for redeemed/revoked tickets.

**Security model**; intentional, don't change:
- All Supabase reads/writes go through the service-role admin client (bypasses RLS).
- **RLS is enabled on every table** (since 2026-07-05). The only anon policies are SELECT on non-private `events` and on `ticket_tiers` of non-private events. New tables must enable RLS in their migration. The exported `supabasePublic` anon client is currently unused by the app.
- **The SQL functions are service-role only** (since 2026-07-29). Every money/capacity function (`reserve_tickets`, `finalize_ticket_sale`, `claim_resale_offer`, …) had the Postgres default `EXECUTE TO PUBLIC` plus explicit anon/authenticated grants, so the public anon key could invoke them through PostgREST rpc with only RLS in the way. They are now revoked from `PUBLIC`/`anon`/`authenticated`, granted to `service_role`, and pinned to `search_path = public, pg_temp`. **New SQL functions must ship with the same three statements** (see the `lock_down_money_functions` migration).
- **Any route keyed by a `walletAddress`/`buyerWallet`/`ownerWallet` param that returns personal data must gate on `requestOwnsWallet`**; a wallet address is public (every shop page links to `/events?veranstalter=<wallet>`), so the param alone proves nothing. This covers reads too, not just writes (`/api/my-tickets`, `/api/loyalty/status`, `/api/profile`, `/api/events/list`, `/api/organizers/status`, `/api/stripe/connect/status`, `/api/credit`). The public profile at `/collection/[wallet]` is the deliberate exception and self-censors via `profiles.is_private`.
- **Admin routes go through `requireAdmin(req)`** (`src/lib/adminAuth.ts`): constant-time secret comparison plus a per-IP throttle of 10 **failed** attempts/minute, so one guessable secret can't be brute-forced. Correct secrets are never throttled (the dashboard polls several of these). Used by all `/api/admin/*` and the manual `/api/tickets/mint`.
- **Bot protection (Vercel BotID)** on the abuse-prone entry points, since 2026-07-29. Three parts that must stay in sync: `withBotId()` in `next.config.ts` (proxy rewrites), the path list in `src/instrumentation-client.ts` (client challenge), and `isBot()` from `src/lib/botCheck.ts` called at the top of each listed route (`/api/checkout/pass` included since the season pass shipped). A path declared in one place but not the others is decorative. **Both halves fail open on purpose** — these sit on the checkout and mint paths, so an outage, a misconfiguration or a plan without BotID must never stop ticket sales; the rate limiter below keeps working regardless. Only `checkLevel: 'basic'` is used (Deep Analysis is a Pro-plan feature). Door routes are excluded (a scanner isn't a browser session we control) and so is `/api/track`.
- **Best-effort rate limiting** via `src/lib/rateLimit.ts` (in-memory, per warm instance) guards the abuse-prone unauthenticated/entry routes: `/api/checkout/create` and `/api/checkout/pass` (reservation exhaustion), `/api/claims/create`, `/api/organizers/apply`, `/api/track`, `/api/waitlist/join`, `/api/tickets/backup`, `/api/resale/*`. Not a hard global quota; back with Redis if a stricter limit is ever needed. `/api/checkout/create` uses **two buckets** (since 2026-07-30): a coarse 60/min per IP — a whole venue behind one NAT must not throttle itself out of a sale — plus a tight 8/min per buyer identity (queue token preferred over the client-claimed `buyerWallet`, which an attacker can invent; guests have neither and rely on the IP bucket). Don't collapse these back into a single per-IP limit.

### Buyer-facing languages (German + English, since 2026-07-29)

**No locale prefix in the URL.** An `app/[locale]/` restructure would collide
with the root dynamic segment `src/app/[handle]/page.tsx` — `/en` and `/@name`
are the same shape and routing cannot tell them apart. The language lives in
the `passly_lang` cookie instead. Price of that: English pages are not
separately indexable; retrofit with a middleware rewrite if EN SEO ever matters.

- `src/lib/i18n.ts` — dictionary + `t(lang, key, vars)`. Client-safe (no `next/headers`). German is the source of truth: `en` is typed as `Record<keyof typeof de, string>`, so a missing English string is a **compile error**, and `t()` falls back to German rather than printing the raw key at a buyer.
- `src/lib/i18nServer.ts` — `getLang()` / `getT()` for server components. Reading the cookie opts a route out of static rendering; fine for buyer pages (they all hit the DB per request), not for anything that must stay static.
- `LangProvider` (fed by the root layout, so no wrong-language flash) + `useT()` for client components; `LangSwitch` is the DE/EN toggle and sits in `LegalLinks`, which every buyer card page already renders.
- **Scope is the buyer surfaces only.** Dashboard, doorman, admin and the legal texts stay German by decision: they are read by German organizers, and a half-translated legal page is worse than a German one.
- **E-mails carry the language on the order**, not on the request: the confirmation goes out minutes later from the mint worker. `mint_jobs.lang` / `guest_orders.lang` / `waitlist_entries.lang` are written at checkout (session metadata `lang`) and at waitlist signup. Reminder and waitlist mails are one body to many addresses, so their senders **group recipients by language** and send one batch per group.

### Positioning & marketing pages (since 2026-07-30)

- **The landing page `/` sells to organizers, not guests.** Guests never choose a ticketing provider; they arrive on `/shop/[id]` from the organizer's own link and never see `/`. Guest discovery lives on `/events`, the public `@handle` profiles and `/so-funktionierts`, reachable from the nav, the guest strip and the footer. Don't turn the hero back into "Events entdecken".
- **The positioning is ownership, not anti-counterfeiting**: the organizer keeps their brand (`@handle` page, accent colour), their money (no percentage cut; the service fee is buyer-side by default and the organizer chooses per event) and their rules (resale markup cap, payout hold, door). Three pillars on the page, in that order. The rotating QR is a proof point under pillar 3 — a feature every competitor claims and not what makes anyone switch.
- **Pro features are marked as Pro** in a separate block, never mixed into the free pillars. `ProPrice` (`src/app/components/ProPrice.tsx`) reads the price from `/api/organizer/billing/price`, i.e. from Stripe, so marketing can't quote a price Checkout doesn't charge. Stripe always wins; the hardcoded **29 €/month** in that file is only the fallback for the window before `STRIPE_PRO_PRICE_ID` exists. **Create the Stripe Price at 29 €** — if the two ever disagree, the page silently shows Stripe's number and the fallback is stale.
- **`/preise` is the canonical pricing page.** `FeeCalculator` (`src/app/components/FeeCalculator.tsx`) computes with the real `serviceFeePerTicketCents`, so the advertised fee can't drift from the charged one. **No competitor fee comparisons** anywhere: their schedules change, and a wrong comparative claim is a UWG risk in Germany, not just sloppy.
- **No fabricated social proof** while there are no real customers: no logo walls, no testimonials, no "X Veranstalter vertrauen uns". The trust bar states only verifiable facts.

### Conventions

- **Design system ("Tokn Based" light template, fully migrated 2026-07-06)**: light theme, violet accent via `--hue: 285`, Geist fonts. Design tokens (`--ink*/--surface*/--accent*`, radii, shadows) **and** the shared component CSS (`.topbar`, `.card`, `.btn`, `.chip`, `.event-card`, `.modal`, `.drawer`, `.field/.input`, `.aurora`, utilities …) live in `src/app/globals.css`. `Icon` (stroke icon set) and `Spark` (sparkline) live in `src/app/components/passlyUi.tsx`. Page archetypes: app pages = `.app > .topbar > .main > .aurora + .container` with `.hero`; mobile pages (ticket, doorman, shop, claim, success) = centered card on `radial-gradient(1000px 500px at 50% -10%, var(--accent-wash), transparent 60%), var(--surface-2)`.
- **No pill shapes** (since 2026-07-27): text-bearing badges must never use `border-radius: 999px`. Hero/section eyebrows carry no container at all (plain accent text, `text-transform: uppercase; letter-spacing: 0.08em; font-weight: 600`); chips/tags/status labels use a square-ish 5–9px radius (6px small, 8–9px larger/clickable). Fully round is still correct for genuinely round things: progress/capacity bars, avatars, status dots (`.chip .d`), circular icon badges. Reason: the rounded pill badge is a well-known "vibecoded app" tell; the information stays, the capsule goes.
- **Language**: all user-facing copy is **German** (getpassly.de), du-Form. No crypto/web3/Solana wording anywhere in the UI; framing is "fälschungssicher"; say "Konto"/"Ticket" instead of wallet/NFT.
- **Styling**: page-specific styles go in inline `<style>{`...`}</style>` blocks referencing the global tokens/classes. Don't introduce Tailwind utility classes on new pages. **A bare `.btn` has no background and no border** (`globals.css`) — it is only a layout base; every button needs `.btn.primary`, `.btn.ghost` or `.btn.subtle`, or it renders invisible.
- **Fonts**: Geist + Geist Mono loaded once in the root layout (`--font-geist`, `--font-geist-mono`, referenced as `--font`/`--mono`). No other fonts.
- **Client vs server**: Most pages are `'use client'` because of Privy hooks. Server components are limited to the root layout, `/`, `/events`, `/shop/[id]/page.tsx`, `/tickets/[assetId]/page.tsx`, `/collection/[walletAddress]` (data fetching) and all `/api/*` routes.
- **SEO**: `src/app/sitemap.ts` (public events, `force-dynamic`; never let it go static or the event list freezes at build) + `src/app/robots.ts` (app/admin surfaces disallowed; keep sitemap and robots consistent; an auth-gated route must not appear in the sitemap). `/shop/[id]` builds per-event OG tags in `generateMetadata`. Route handlers without request APIs (e.g. `/api/organizer/billing/price`) need `export const dynamic = 'force-dynamic'` or Next prerenders them at build time.
- **Stack versions**: Next.js 16 App Router, React 19, Tailwind 4 (PostCSS only, no config file). Don't suggest patterns that assume older versions.
